scene 01 · form builder

what you're looking at

A working sign-up form built with createForm. Five fields, four validators, one cross-field rule (confirm depends on password via ctx.get).

Type into any field — the right panel shows every reactive read firing. The last keystroke ran counter is the headline: typing in one field runs exactly one validator, regardless of how many other fields have validators.

what to try

Type "x" into email → "invalid email" appears.
Type more letters → the error stays "invalid email" and the row doesn't flash in the state panel — that's the Object.is cutoff not propagating to the DOM because the message hasn't changed.

Type a valid email → error clears once.
Keep typing → no further renders (allocation-free).

Submit while invalid → all errors reveal at once (submitAttempted flips). Submit when valid → the console logs a fake API call.

scene 02 · validator storm

what this shows

A form with N fields, each with its own per-field validator AND a "render" subscriber. Type into f0 only.

Watch the top-left counter: it stays at 1 no matter what you type, no matter how many fields exist. The other N−1 validators are not called — their error() computeds short-circuit on the reveal gate before reading rawError.

This is why typing in one field of a 100-field form is O(1).

scene 03 · submit wizard

what this shows

The full submit() lifecycle, narrated. Pick a simulated server outcome on the form, hit "charge" with any data — the right column traces every state transition.

Notice: a ReferenceError thrown inside onSubmit is re-thrown (it's a structural bug, not a submission outcome). A TypeError (fetch network failure) is captured as submitError — same for any plain Error.

edge cases

Force reveal sets submitAttempted = true directly. Useful for "are you sure?" preview steps that need to highlight invalid fields before the real submit.

Reset wipes touched, dirty, submitAttempted, AND submitError in one batched update.

Submit while invalid → blocked synchronously, onSubmit never runs. Try it: empty the email and click charge.

scene 04 · vs hand-written

what this shows

Both panels do the same workload: N fields each with a validator, then 5000 simulated keystrokes per tick on one field.

Green uses lite-form. Only f0's validator runs per keystroke.
Magenta is a handwritten setValue that re-runs every validator and notifies every subscriber on every change — the pattern Formik defaults to.

Charts plot microseconds per keystroke. Lower is better. The handwritten line scales with N; lite-form's is flat.

control

Each tick fires 5000 keystrokes against each side and times them. Increase N to see the handwritten line climb while the lite-form line stays put.
